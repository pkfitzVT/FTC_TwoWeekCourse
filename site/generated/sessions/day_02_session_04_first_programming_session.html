Day 2, Session 4: First Programming Session

Purpose

Introduce how FTC software connects driver input, Java code, configuration names, and physical robot hardware while teams finish the strategy and robot-behavior bridge needed before chassis design.

Learning Target

Students can explain how a simple TeleOp program connects the Driver Station, OpMode, hardware map, and robot hardware.

Success Criteria

  • Students identify the OpMode name.
  • Teams complete or update the Team Strategy Guide.
  • Teams complete or update the Robot Behavior Specification.
  • Students identify hardware names in code.
  • Students explain that configuration names must match quoted names in Java.
  • Students record one predicted or observed robot behavior.

Teacher Preparation

Prepare Robot Controller and Driver Station devices, OnBot Java access, example TeleOp code, hardware configuration examples, batteries, safe test blocks, a safe test area, the Game Strategy SLD, the Strategy-to-Robot-Behavior SLD, Demo Robot Design Analysis notes from Sessions 1-2, the Team Strategy Guide, the Robot Behavior Specification, and the SLD tally sheet.

Student-Led Discussion / Decision

Run the strategy bridge before major chassis choices:

1. Game Strategy SLD: What strategy gives our team the best chance to score reliably, avoid penalties, and complete a working robot in the time available? 2. Strategy-to-Robot-Behavior SLD: What specific robot behaviors must our robot perform to make our strategy possible?

Students should use Demo Robot Design Analysis evidence when discussing what seemed reliable, what seemed difficult, which strategies felt realistic, which robot behaviors seemed easy or hard, and which behaviors depended on driver/operator coordination.

Programming prompt: Why must the names in the configuration file match the names in the program exactly?

Work Time Options

  • Strategy: complete or update the Team Strategy Guide.
  • Requirements: complete or update the Robot Behavior Specification.
  • Evidence: identify demo robot features that support or challenge the proposed strategy and required behaviors.
  • Programming: read and annotate the drive-only D-pad and joystick TeleOp examples.
  • Testing: run only if hardware is ready and safely lifted.
  • Documentation: map hardware names, motor ports, variables, and controls.

Must / Should / Could

  • Must: Record a first game strategy, required robot behaviors, one piece of demo robot evidence, OpMode, hardware names, variables, and gamepad inputs in a drive-only TeleOp.
  • Should: Make one small documented code or configuration change.
  • Could: Add telemetry or comments that make the code easier for a teammate to understand.

Deliverables

  • Team Strategy Guide update.
  • Robot Behavior Specification update.
  • Code notes or screenshot.
  • Configuration-name table.
  • Test result if hardware is ready.
  • Engineering portfolio entry.

Engineering Portfolio Evidence

Teams should add the strategy decision, robot behavior specification, OpMode name, configured hardware names, motor ports, gamepad controls, one code change or prediction, and result. They should identify which demo robot evidence influenced the strategy or behavior plan.

Reflection / Share-Out

  • What part of the code/configuration chain must be correct for safe movement?
  • Which later design choice will be most affected by the team's strategy or robot behavior plan?

Teacher Notes

Keep first code changes small. Prioritize safe testing and conceptual understanding over driving speed.
